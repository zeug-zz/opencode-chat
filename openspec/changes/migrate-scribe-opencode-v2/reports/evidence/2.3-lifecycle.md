## Implementation

- `OpenCodeAgent.connect()` now serializes a new launch behind a still-resolving startup and any in-flight cleanup. Cleanup rejection propagates and prevents a new child from starting.
- A startup generation invalidated by disconnect/reconnect prevents a late-ready child from publishing a client. The child is closed/reaped; reconnect then starts the selected backend again. The generation check applies to both unsandboxed and sandbox-wrapper launch paths. No prompt is replayed.
- Existing child lifecycle callback handling invalidates the client and does not change the selected backend. Existing helper readiness rejects authentication, identity, version and location mismatches; post-ready operation errors remain operation errors, not plugin-startup retry signals.
- Credential values are passed only through private helper headers/in-memory child environment and the new tests use dummy credentials; no diagnostics or manifests contain them.

## Native fallback source review and blocker

Reviewed pinned public sources at commit `843a6c514e606b436a7fe713422ace0a93ad3d61`:

- `packages/core/src/plugin.ts` exposes `Plugin.Service.activate(plugins, failures)` and plugin inventory/state. This is the activation service, not proof that a configuration overlay removes all plugin definitions or discovery sources.
- `packages/core/src/config/discovery.ts` discovers system, managed-preference, global, explicit-file, direct, project, `.claude`, and `.agents` sources. `packages/core/src/config.ts` loads well-known config plus those sources with precedence. This makes a guessed `plugin: []` overlay insufficient evidence that all autodiscovery is cleared.
- Local source retrieval of the originally named `packages/core/src/plugin.ts` via the repository's local git object database was unavailable (`git show` reports that path absent); the pinned public raw source was inspected read-only instead. No source-backed operation was found here that conclusively removes plugin definitions across all config/discovery sources while retaining all other policy.

Therefore no classifier, retry, or synthetic plugin-free overlay was added. Auth/version/identity/location/startup/network/cleanup failures remain non-retryable, and there is no downgrade or same-backend fallback claim. Implementing eligible fallback and clearing provider, lifecycle-hook, native-config, and host capability authority requires the native overlay/removal contract in local port 3.1/3.4 before this task can be completed.

Status: **STATIC SOURCE ANALYSIS ONLY — eligible native plugin-free fallback remains BLOCKED.** The inspected source is release tag `v2.1.2`, commit `a517687fde98a7329ada3ae644a01a9fc6c4e99e`, extracted under `tmp/scribe-v2-migration/rebaseline-2.1.2/native-source/extracted/`. This is source-pin evidence, not proof that the installed executable is equivalent to that source or runtime qualification. See `reports/evidence/1.1-rebaseline-2.1.2.md` for artifact provenance.

- `packages/core/src/config/plugin/source.ts:113-119` parses a leading `-` as a removal operation. At lines 127-159 it discovers modules from directories before applying configured plugin operations, which are applied last.
- `packages/core/src/plugin/supervisor.ts:39-96` processes removals after earlier `modules.load` calls. `-*` clears the failure list and disables matching non-guarded plugins; it does not undo module evaluation or establish absence of its side effects.
- `packages/core/src/plugin/internal.ts:254-276` shows ordinary configuration/instruction/agent/provider/tool plugins in the post list. Only the Console connection and policy plugins are guarded. Thus `-*` is not a harmless clear-all: it also disables essential ordinary behavior.
- A `-*` or `opencode.*` selector is not proof of safe external-plugin removal or an authority guarantee. The selector is applied late in the supervisor lifecycle, after module loading; it does not establish a fresh plugin-free process.

The official V2 plugin documentation describes removal support: https://opencode.ai/v2/docs/plugins. That documented operation does not establish the stronger removal-timing, side-effect, discovery, or authority guarantees above. No retry classifier, synthetic replacement discovery, or permission alteration was added. Native fallback and installed identity/source/version gates remain **BLOCKED**; source and metadata observations are not runtime evidence. The existing 2.1.2 helper/happy-path PASS does not close either fallback gate.

## 2026-10-23 — Native plugin-failure fixture tooling (runtime NOT_RUN)

Status: **TOOLING ONLY — native runtime NOT_RUN; no fallback claim.** Added `packages/agents/opencode/src/__tests__/v2-plugin-failure.integration.test.ts`. Default (unset-env) run covers pure tests only: fixture module behavior, owned-config plan drift, `plugin.list` classification negatives, config-fingerprint diff, forbidden-content scan, and a strict manifest verifier with per-check/cleanup/count/observed negatives. The opt-in test is skipped unless `OPENCODE_CHAT_RUN_V2_ADAPTER=1` and an absolute `OPENCODE_CHAT_V2_SPIKE_EXECUTABLE` are set; the primary runs it.

Native 2.1.2 source (inspected tag, read-only) the fixture is designed around:

- `core/src/plugin/supervisor.ts:33-120` — `modules.load` errors are caught by `Effect.catchCause`, logged, and recorded in `failures` as `{source:{type:"local",path:<package dir>}, state:{status:"failed",error,ref}}` with no `id`; resolution proceeds, so a load failure does not fail startup.
- `core/src/plugin/module.ts` — default export must be `{id, effect}` or `{id, setup}` (else `LoadError`); local directories resolve a `server` entry with extension probing, so each fixture package has `package.json` (`"type":"module"`) plus `server.js`.
- `core/src/plugin.ts` `load()`/`activate()` (~45-215) and `slotInfo()` (~280): a setup/effect that throws is caught by `Effect.exit`, logged, and stored as a slot `error`; `plugin.list` then reports `{id, source:{type:"local",path:<entry file>}, state:{status:"failed",error}}` (no `ref`) and other plugins still activate. Activation runs under `registry.hold()`; `awaitActivation` reopens after the burst, so the fixture polls `plugin.list` (bounded) rather than trusting the first read.
- `core/src/config/plugin/source.ts:113-160` — plugin operations accumulate across documents; `plugins: []` in a later document removes nothing; `-target` removal applies after modules load (unchanged from the blocker analysis above).
- Not established statically: the HTTP readiness gating itself was not traced to a source line beyond the activation hold; the fixture records whether connect succeeds (`connectSucceededWithFailingPlugins`) rather than assuming it.

Fixture design: one production `OpenCodeAgent` private child (sandbox off, no OS claim, `pluginSources: []`), local mock provider (1 model request), owned isolated global config only, four generated local plugin packages referenced by absolute path: `throws-on-import` (top-level throw), `invalid-export` (default export without id/effect/setup), `activation-throws` (valid `{id, setup}` whose setup rejects), `control` (valid, expected `active`). Expected native state recorded per fixture: load failures `failed` with no id; activation failure `failed` with id `fixture.activation-throws`; control `active` with id `fixture.control`. A deviation is recorded as the exact observed enum and the run is FAIL (not forced PASS). Also asserted: connect succeeds at 2.1.2, Scout prompt completes busy→idle, `agent.getToolIds()` returns `[]`, plugin states unchanged after the run, no config file bytes/mtime changed/added.

Bounds: 90 s overall, 40 API requests, 1 model request, 1 session, 1 child, 12 plugin-list reads, 512 KiB model body. Manifest: `tmp/scribe-v2-migration/plugin-failure/<uuid>/result.json`, mode 0600, strict read-back verifier, pre-teardown freeze, cleanup gates (agent disconnect, process group gone, fixture closed, isolation removed, state/database absent, env/fetch restored). Persists only booleans/enums/counts and owned relative paths; no plugin error text, absolute paths, config or environment.
