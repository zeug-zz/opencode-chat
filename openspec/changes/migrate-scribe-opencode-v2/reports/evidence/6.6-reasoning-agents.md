## Implementation

- Added hidden native `chat-reasoning-critic` and `chat-reasoning-verifier` targets. Both use `mode: "subagent"`, two steps, the native default model, and fixed instructions embedding closed JSON schemas with at most three entries, bounded targets/reasons/objections, and no extra keys. Scout guidance calls them only when warranted, at most once per active user turn, and treats their output as untrusted.
- Scout's effective overlay allows only `chat-research-worker`, `chat-reasoning-critic`, and `chat-reasoning-verifier` as `subagent` targets. Write is excluded. The bundled plugin's `agent.transform` removes configured non-deny broad/task/subagent Scout grants and reasserts only those exact targets.
- The plugin fails closed for reasoning-target `permission.evaluate` events and tracks exact critic/verifier calls by session/turn. Since OpenCode 2.1.4 can reuse a prior native allow without re-running `permission.evaluate`, `tool.hook("execute.before")` also denies a repeated actual invocation. A second permission hook denies all actions for calls attributed to either reasoning agent. State is bounded, cleared on turn changes/disposal, and unrelated permission decisions remain untouched.
- Completed foreground reasoning `subagent` results are capped at 2,048 characters in `execute.after`, including string/array text content and a fixed truncation marker. Background completion arrives through `sessions.synthetic`, outside the tool hook, and is not covered by this cap.
- Updated host security-negative guards to match the exact three Scout delegation grants in the in-memory overlay, and added the new `execute.before` hook to the host test plugin context.
- The fixture imports the denial strings exported by the plain-JS plugin and records only category/length/attribution, never denial or child text. Its `scribe_reasoning_denied` category matches the exact fixed plugin denial strings before applying the pre-existing native-denial patterns.
- Composite plugin SHA-256 is `e2b83183e50145878b6449c508ce70fbacab0641766a6e568497932b6fa8673d`, computed over `package.json\0` + manifest bytes + `\0server.js\0` + source bytes. The extension and integration-test pins match.

### Effective reviewer permissions (original 2.1.4 baseline)

The pinned native effective profiles are hidden, `mode: "subagent"`, have no model override, and retain explicit wildcard and `execute` denies. They also expose the same four non-deny rules in `agent.list` for both reviewers; the 2.1.4 `Agent.Info.default` defines this native default permission prefix (`packages/schema/src/agent.ts` at the pinned tag):

| Action | Resource | Effect |
|---|---|---|
| `*` | `*` | `allow` |
| `read` | `*.env` | `ask` |
| `read` | `*.env.*` | `ask` |
| `read` | `*.env.example` | `allow` |

The original 2.1.4 manifest records bounded action/resource/effect tuples and indexes, asserts the exact pinned baseline at positions 0–3, and verifies the following 26 rules are all denies, including wildcard and `execute` denies (`reasoningProfileNonDenyRulesAreShadowedByLaterDenyBaseline: true`). Native last-matching-rule semantics shadow the four defaults with the later explicit deny baseline; any new or reordered non-deny rule fails qualification. The plugin transform filters configured non-deny rules, but the final native profile still exposes this prefix, so the effective profile is **not** claimed to be deny-only and `criticIsHiddenDenyOnly` / `verifierIsHiddenDenyOnly` remain false. The strict consequence checks are the exact default prefix and deny ordering, zero provider tool definitions for every reasoning child, and deterministic plugin-hook tests that force every evaluated action to deny for both reviewer agents. Do not treat the four native rules as evidence that reviewers have usable tools.

### Repeat attribution and limits

For both foreground and background repeats, the fixture saw the fixed `REASONING_SUBAGENT_DENIAL` result in the parent Scout provider continuation and records `parent-scout-session`; the child-attributed `REASONING_SUBAGENT_TOOL_DENIAL` path was not observed. The plugin hook callback event itself is not exposed by the native fixture, so it does not distinguish which of `permission.evaluate` or `execute.before` produced a given repeat error. The native behavior and plugin guard explain why both hooks are present; the reported parent-versus-child attribution is based on the exact fixed denial branch and parent-session continuation, not a captured callback payload.

The background result cap is a known product limitation, not a failed assertion or a claim of background bounding: OpenCode 2.1.4 sends background completion through `sessions.synthetic`, which is outside `execute.after`. Foreground results remain capped and the residual remains explicitly checked.
