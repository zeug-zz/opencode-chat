## Static operation and implementation mapping

This section supersedes the earlier statement that the package did not expose a route table. The published entrypoint reexports into bundled implementation code; inspection of `dist/chunks/shared-events-hqeq47hr.js` provides static HTTP verbs and paths, and `dist/chunks/shared-events-2ny4vxct.js` provides static service-probe/auth construction. These are package implementation facts only, not runtime claims. Static output fields below refer to exact generated declaration names in `dist/promise/generated/types.d.ts`.

### Client, auth and server identity

- `ClientOptions` is `{ baseUrl: string; fetch?: typeof globalThis.fetch; headers?: RequestInit["headers"] }`. `RequestOptions` supports `signal?: AbortSignal`, per-request headers and SSE `onActivity`. Bundled request preparation resolves descriptor paths against `baseUrl`, adds query parameters, merges global and request headers, JSON serializes non-binary body, sets content type and passes request `signal` to `fetch`. SSE parser requires `text/event-stream`, reads stream chunks and invokes `onActivity`; this proves client-side mechanics, not live-only/reconnect semantics.
- `GET /api/info` (`server.info`) returns `ServerInfo { version, pid, urls, paths: { tmp }, capabilities? }`; generated descriptor declares 200 and 400/401. It statically exposes identity/version/URLs, but whether it uniquely binds the spawned child remains runtime work.
- Service static types (`dist/service.d.ts`) define `Info { url, pid, password?, version?, id? }` and optional basic auth credentials. The bundled service probe (`dist/chunks/shared-events-2ny4vxct.js`) builds Basic auth with username `opencode` and the registered private password, probes `GET /api/info`, and checks pid/version. That is explicit static evidence for the package service-registration contract, **not** proof that standalone foreground `opencode serve` provisions or accepts those credentials. `opencode serve --help` advertises no auth flag. Scribe must not call or adopt the shared-service registration/probe flow.

### Exact static schema refinements and true gaps

- Prompt’s full `SessionPromptInput` requires `sessionID` as the route parameter and `text` in the request body; body fields `id,files,agents,skills,metadata`, `delivery` and `resume` are optional. The request type does not expose model/provider/variant/system/tools. Thus `switchModel` and `switchAgent` exist as explicit session operations, but prompt-time options cannot be silently projected into the prompt body.
- `SessionSwitchModelInput` requires `sessionID` and `{ model: { id, providerID, variant? } }`; `SessionSwitchAgentInput` requires `sessionID,agent`. `SessionCreateInput` separately accepts agent, model, location directory and permissions. The release schemas establish mechanisms, not whether pre-prompt setters are race-free or preserve intended per-message model selection.
- Native instruction candidate is `session.instructions.entry.list/put/remove`: GET `/api/experimental/session/{sessionID}/instructions/entries` returns `InstructionEntryInfo[]` with key and arbitrary `JsonValue`; PUT `.../entries/{key}` takes `{value: JsonValue}` and returns 204; DELETE same key returns 204. `SessionInstructionsUpdated` is in V2 event unions. This makes a session-scoped instruction-entry API statically inspectable. **Still unresolved:** permitted key/shape for system instructions, model-visible semantics, ephemeral vs persisted/session-exported data, effect ordering relative to prompt, cleanup/reconnect, and safety for hidden brief content. Therefore it is only a candidate, not proof of the required dynamic brief channel.
- `SessionFormReplyInput` schema exists, but form/question integration semantics, identity contract and cancellation behavior remain unproven. Export/import schema is exact statically, but import side effects/identity and independent TUI compatibility are not runtime-proven.
- Config `GET /api/config` returns array of document entries with `path?` and `info`; current published generated output is materially not a generic `AppConfig`. `PATCH /api/experimental/config` only has `shell` in this generated input. Config precedence/effective permission composition still needs server source/effective behavior proof.
- MCP `McpServer` and `McpAddInput` expose definitions; static method contracts do not establish merge/precedence. Full definition handling must not be mistaken for proven native overlay or managed-denial semantics.
