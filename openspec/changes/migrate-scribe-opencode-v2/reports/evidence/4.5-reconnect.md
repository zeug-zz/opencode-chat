# 4.5 Reconnect refresh — bounded pending-interaction adapter slices

Status: **PARTIAL — native pending questions and permissions are rehydrated on each valid `server.connected` marker, and the UI/host now reset stale pending-interaction state at that boundary.** Host active-session/message refresh, queues, and real reconnect qualification remain deferred; Task 4.5 remains unchecked.

## Implemented

- Extracted native `FormInfo`-to-`QuestionRequest` validation/mapping into a pure helper shared by `form.created` events and reconnect hydration. `createV2EventMapper()` retains its callable API and now exposes a small hydration method that seeds the same per-subscription question-form registry; unknown form kinds and malformed records remain ignored.
- Question-form snapshots are staged and validated before mapper state changes. Duplicate IDs, conflicting already-seeded records, and malformed records marked `metadata.kind === "question"` reject the refresh; unrelated form kinds are ignored. Identical forms already observed from live events are not emitted again.
- Extracted native permission-request-to-domain mapping into a pure helper shared by `permission.asked` events and hydration. Native permission `resources` and `save` arrays are validated as strings (not bounded IDs), preserving long valid resource paths. Only the request's public metadata and native tool identity are mapped; event-envelope metadata is excluded.
- On each valid native `server.connected` frame, the adapter emits the marker first, then awaits both `client.form.list({ location }, { signal })` and `client.permission.request.list({ location }, { signal })` before processing later stream frames. Both response locations must exactly match the catalog workspace and the current client/connection/stream generation must still be active. Hydrated question pending state is registered before listener delivery; mapper question/permission registries suppress following duplicate live `form.created` / `permission.asked` frames and clear on corresponding reply/cancel events.
- A stale snapshot is discarded. Wrong-location, malformed known-question, or failed interaction snapshots report only `OpenCode pending interactions could not be refreshed; Chat is unavailable.` No empty-list success is fabricated, no prompt is replayed, and no prompt admission/API-write behavior changed. Permission events retain identity/source/save/metadata for existing host routing; the adapter itself does not claim host/UI behavior.
- Both pending-interaction hooks clear their old maps on `server.connected`; replayed `permission.asked` / `question.asked` events repopulate them using the existing active-session filter. This emits no synthetic reply/rejection. On the host, reconnect invalidates every old retention confirmation record before subsequent hydrated asks; a replayed valid request is revalidated through the existing summary validator, remains redacted from the webview, and clamps `always` to `once`. A reply to a removed stale ID is rejected. Prompt queues and the active session are untouched.
