# 2.5 domain mapping — provider/agent/skill chunk

Status: **PARTIAL implementation only; task 2.5 remains unchecked.** This chunk ports provider/model catalog, agent list, and skill list reads to the pinned native `@opencode/client@2.0.32`. It does not address capabilities, diff/todo, path/config, tools/MCP, route gating, or other 2.5 methods.

## Implemented

- Provider and model catalog calls use native `provider.list`, `model.list`, and `model.default`; requests explicitly pass the active workspace location and reject responses bound to another directory.
- Native provider `id`/`name` map to domain provider identity. Provider `env` names come only from matched `IntegrationInfo.methods` entries with `type: "env"`, using declared names—not connection labels, env values, credential IDs, or credential APIs. Duplicate integration IDs and malformed env names fail with generic bounded errors. Model `modelID`/`providerID` map to domain model key/provider grouping. Model name, context/output limits, status, attachment/reasoning/temperature/tool-call flags, default (untiered) per-million-token costs, and variant identifiers are mapped. Context-tier costs are excluded from the domain's flat cost fields; variant settings/headers/body are intentionally omitted because the domain only uses variant IDs and opaque variant values could include sensitive configuration.
- Native agents map the operational native `id` to domain `name` (the UI sends this value back for agent selection), plus mode, description, and color. Hidden agents are omitted because the domain has no hidden flag; request/system/permissions are not copied. `builtIn` is omitted because native `AgentInfo` does not establish it. Native skill `name` remains the domain name because the UI invokes skills by slash-name; the unrelated native skill ID is not substituted. Skill content remains excluded.
- Native skills map name, description, and actual path to domain location. Skill content is intentionally not copied into the domain catalog.
- Native `integration.list` metadata is joined to provider `integrationID` (falling back to provider ID as the pinned provider source does). The domain `connected` list represents native configured availability, not network health: disabled activation is excluded; enabled activation is available; auto activation with any connection is available (including `needs_auth`); a provider without any integration remains available anonymously. A reauth/runtime error does not silently hide an otherwise available catalog entry. No credential listing, secret resolution, or network probe is used.

## Outstanding mapping risks

- If no matching native integration is returned, required domain provider `env` is `[]` (no declaration observed), not a claim that no environment requirement exists. Native modality semantics are represented as `attachment` when non-text input exists and `reasoning` when output includes `reasoning`; conditional context-tier costs remain unavailable in the flat domain shape.
- Unknown extra metadata fields are ignored while required mapped fields and response locations are validated; malformed mapped fields fail with bounded generic errors. Review whether unknown-field rejection is needed after confirming the exact server response contract.
- 2.4 share/unshare remains an independent mandatory API gap and is not addressed or closed by this catalog work.

## Native session diff follow-up

- `getSessionDiff()` now calls only the captured V2 client's `session.diff({ sessionID })`. It validates the requested session first using the same captured client and `mapV2Session` with the requested ID and captured workspace, then rejects stale connection/workspace results and session deletion observed before the diff result is accepted. The adapter returns a mapped native array; no legacy SDK envelope or fallback is used. `sessionDiff` is enabled; other capability flags are unchanged.
- Native-source basis: pinned client `FileDiffInfo` is `{ file, patch, additions, deletions, status }`; native `SessionDiff.turn` defaults omitted context to `PATCH_CONTEXT_LINES` (`2_147_483_647`), and snapshot Git generation uses that context. `vcs/patch.ts` sets 10,000,000-byte per-patch and aggregate limits; Git can replace truncated/aggregate-capped patches with an empty patch. Git and Mercurial tracked diffs use Git-format output; Mercurial untracked/missing patches are synthesized through `formatPatch`/`addPatch`/`deletePatch`. The latter representation has not been runtime-verified here, so no all-VCS parity claim is made. The mapper parses a single full-file Git-format hunk, checks header order, starts/counts/status/counters, requires a final patch LF, preserves CRLF payload and valid newline markers, and uses native `file` literally rather than deriving paths from headers.
- Native binary patches, truncated/capped output that lacks a reconstructable full patch, malformed/inconsistent headers or hunk counts, and partial/multiple hunks are rejected with the fixed opaque error `Invalid or unsupported OpenCode V2 session diff.` No contents are fabricated for those cases. Empty added/deleted files with zero counters and metadata-only `new file mode`/`deleted file mode` patches map to empty contents. Modified mode-only changes without reconstructable content are rejected; this mandatory diff case and binary/capped cases remain unqualified, not silently treated as success.

## Native formatter-style patch correction

- The pinned `vcs/patch.ts` uses `diff.formatPatch(structuredPatch(...))` for `emptyPatch`, `addPatch`, and `deletePatch`; Mercurial untracked/missing content uses the latter two helpers. The mapper now accepts the verified formatter header shape (`Index: …`, separator, ordered `---`/`+++` with equal path tokens) for nonempty, complete single-hunk patches, including added/deleted hunks whose old/new paths are equal. It continues to derive all contents from hunk rows and uses native `file` as the returned path without header-path derivation or file access.
- Formatter-style no-hunk patches are always rejected: native `emptyPatch` is also used for capped or unreadable content, so zero counters cannot distinguish an actually empty file from omitted contents. Git-style metadata-only empty added/deleted files remain accepted only with the corresponding file-mode header and zero counters. Binary, capped/truncated, ambiguous formatter-empty, and modified mode-only patches remain unqualified mandatory diff cases; no content is fabricated and full diff parity is not claimed.
